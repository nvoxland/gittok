# Stories row, notifications, offline, LAN (M5 contract)

## Stories row (SPEC §7.4)

`GET /api/stories` → `{"stories": [Story]}`, one per configured repo that has commits in the last 24 hours (wall clock), newest first:

```json
{"repo": "storefront", "mascot": "otter", "mascot_image": "/assets/mascots/otter.png?v=<mtime>" | null,
 "commits": [{"sha": "<full>", "short": "abc1234", "ts": 1700000000, "author": "Alice Archer", "subject": "Fix ...", "files": 3}],
 "seen": false}
```
- At most 10 commits per repo, from `git log --since=@<now-86400>` on the repo ref (via gitq), cached per repo head sha.
- `seen` is true when every commit sha was already viewed: `POST /api/stories/seen {"repo", "shas": [...]}` records them (table `story_views(repo, sha, seen_at)`).
- The web shows a horizontal row of circles (mascot image or initial) at the top of the feed; unseen repos get a colored ring. Tapping opens a full-screen story viewer: one commit per page (subject, author, time, files count, short sha), tap right/left to move, swipe down or ✕ to close; viewing marks shas seen.

## Notifications (SPEC §7.5)

Table `notifications(id, kind, text, card_id, created_at, read_at)` (exists). Generated by a server pass (in the learning worker loop, or its own worker) and `gittok notify`:
- `new_cards`: "12 new cards from storefront" once per finished run with accepted > 0 (link: feed).
- `srs_due`: "2 quiz cards are back for another try" when due SRS cards exist and no unread `srs_due` notification exists. The dedup key is a hash of the sorted due card ids, so it fires once per distinct due set.
- `hot_file`: at most one per repo per UTC day, from the same commits used for stories. Files touched by ≥3 commits in the last 24 h count; paths under dot-directories (`.beads/`, `.claude/`) do not. One file gives "auth.py was in 3 commits in the last 24 hours"; several give a digest, "Busy day in storefront: brief.py (11 commits), cli.py (10), api.py (7) and 4 more". Deduplicated on (repo, date).
- `new_kind`: "A new Spot the Bug from billing/" when a card with story_type `spot_the_bug` lands (link: card). Only cards created in the last 24 hours count.
- Dedup key per notification so passes are idempotent.

`GET /api/notifications?unread=1` → `{"notifications": [{"id", "kind", "text", "card_id", "created_at", "read"}], "unread": n}`; `POST /api/notifications/read {"ids": [...]} | {"all": true}`. The web shows a bell with the unread count in the top bar and a `/notifications` list; tapping one with a card opens `/card/{id}`.

## PWA and offline (SPEC §11)

- `web/static/manifest.webmanifest` (name "GitTok", short_name, theme/background colors, `display: standalone`, icons 192/512 generated as PNG from an SVG at build time or committed), linked from `app.html` with `apple-touch-icon` and `theme-color` metas.
- A hand-written service worker (`web/static/sw.js`, registered from the layout when `'serviceWorker' in navigator`): precache the app shell (build assets list) and cache-first for `/assets/*` images; network-first with cache fallback for `GET /api/feed` (the last successful batch is served offline) and `/api/cards/*`; never cache `POST`s; queue `POST /api/events` while offline and replay on reconnect (Background Sync when available, else on next load).
- An "Offline — showing your last batch" banner when the feed came from cache.

## LAN access

- LAN serving is opt-in. `gittok serve --lan` (or `gittok mcp --ui --lan`, or `server.lan: true` in `local/settings.yaml`) binds `0.0.0.0` and prints the LAN URL(s) (first non-loopback IPv4 of each interface) next to the localhost URL.
- The feed is token-protected. `--lan` creates (or reuses) a random token in `<data_dir>/lan_token` (mode 0600) and prints a pairing URL per LAN address: `http://<lan-ip>:<port>/pair?t=<token>`. Opening it sets an HttpOnly, SameSite=Lax cookie `cs_lan` (long expiry) and redirects to `/`.
- Requests from non-loopback peers need the cookie, except `/pair`. Without it, `/api/*` returns 401 JSON and other paths return a small page that says to open the pairing URL. Loopback peers never need the cookie. The token is compared in constant time.
- MCP (`/mcp`) is loopback-only, always (not only with `--lan`). The server checks the peer address (the Host allowlist is a separate check) and returns 403 to any non-loopback peer.
- Request bodies are limited to 1 MB (413). `POST /api/stories/seen` takes at most 100 shas, each 7-40 hex characters. `POST /api/events` takes at most 500 events, and each event `data` must be 4 KB or less as JSON.
- PWA install and offline mode need HTTPS: service workers do not register on plain-HTTP LAN origins. The feed still works in the browser over HTTP. Tailscale is the planned HTTPS path (M6).
- `settings.server.host` stays `127.0.0.1` and `settings.server.lan` stays `false` by default. A non-loopback `--host` (or `server.host`) without `--lan` is token-protected too: the server makes the token and prints the pairing URL for that host.
- Host allowlist (DNS rebinding). Every path (`/api/*`, `/assets/*`, `/pair`, the web app, `/mcp`) answers only when the `Host` header, with or without a port, is `127.0.0.1`, `localhost`, `[::1]`, one of this machine's LAN IPv4 addresses, its host name (also the short name and `<short name>.local`), or a name in `settings.server.allowed_hosts` (a list, empty by default; use it for a VPN name or an IPv6 address). Any other or missing `Host` gets 421. The address list is read again after 30 s, and at most each 2 s when an unknown Host arrives, so a new LAN address works without a restart.
- Origin check. A `POST`, `PUT`, `PATCH` or `DELETE` with an `Origin` header whose host is not in the same allowlist gets 403. A request without `Origin` passes.
- Response headers on every response: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and a `Content-Security-Policy`: `default-src 'self'; script-src 'self' 'wasm-unsafe-eval' <sha256 of each inline script in the built index.html>; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self'; worker-src 'self'; manifest-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`. The server computes the script hashes from `index.html` (again when the file changes), so the web build needs no CSP config. `'wasm-unsafe-eval'` is for the code highlighter's WebAssembly regex engine; `'unsafe-inline'` styles are for highlighted code and diagrams.
- The uvicorn access log shows `/pair?[redacted]`, never the token.

## Characters that carry

- Pages: `/persona/<handle>` (avatar, name, `bio` from personas.yaml or the voice, recent posts,
  recent comments) and `/file/<repo>/<path>` (commit count, last touched, top authors, cards
  that cite the path in sources, visual, depth panels or `account`). API: `GET /api/personas/{handle}`,
  `GET /api/files/{repo}/{path}`.
- Card headers and comment names link to those pages; a code-account poster links to its file page.
- Follow: `POST /api/follows {repo, path, on}`. Follows are stored in the `prefs` table under
  `followed_paths`. In the slotter, a card whose repo and dir match the dir of a followed path
  (the path itself if it has no file extension) has its score multiplied by `FOLLOW_BOOST` (1.5).
- Comments: the card face shows two comments with avatars. On quiz cards a comment is a spoiler
  (hidden until answered) unless it sets `spoiler: false`.
- Cast notes: `get_packet` returns `cast_markdown`, each packet persona's last 3 hooks or
  comments (trimmed), at most 800 bytes. Writers call back to running jokes.
- Series: `series` is `null` or `{key, part, of}`. The face shows a "Part n/of" chip. The slotter
  holds a part back while an earlier part is unseen, orders parts, and spaces them `SERIES_GAP` (3).
